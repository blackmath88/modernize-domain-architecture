# Executable Domain Knowledge: OSS Precedents

## Conclusion

**INFERRED:** Executable domain knowledge is not a new software category. The closest migration abstraction is a versioned OpenRewrite recipe library, concretely implemented by Apache Camel Upgrade Recipes. OPA policy bundles are the strongest counterexample to treating independently managed, auditable decisions as a new MEDP capability. A new package format is not justified by these capabilities alone.

This is a primary-source review accessed on 2026-09-23, not a runtime benchmark. Documented capabilities are not claims that we executed the tools. Absence from reviewed documentation is not proof of product-wide absence.

## Strongest counterexamples

- **DOCUMENTED:** [Camel Upgrade Recipes](https://github.com/apache/camel-upgrade-recipes) distributes named migration recipes through Maven, composes version-specific migrations, tests several migration paths, and publishes a reusable test JAR. It explicitly excludes Camel-Quarkus applications from this migration route. This is executable, maintained domain expertise without MEDP.
- **DOCUMENTED:** [OPA bundles](https://www.openpolicyagent.org/docs/management-bundles) package Rego and data, carry revisions and namespace roots, support signatures, and prevent ordinary REST writes to bundle-owned policy/data. Verification depends on loading mode and configuration; the documentation says `opa eval` and `opa test` do not verify signatures.
- **DOCUMENTED:** [OPA decision logs](https://www.openpolicyagent.org/docs/management-decision-logs) associate decisions with inputs, results, and bundle revisions. Logs can be masked or dropped; they are not inherently an immutable audit store.
- **INFERRED:** A caller can consume externally owned decisions, but an agent able to change the evaluator, enforcement point, or its credentials can bypass the intended authority boundary. Signing proves origin/integrity under a trust configuration, not correctness or permission to execute a transformation.

## Method and scope

The comparison below covers all twelve families in the [WS-03 brief](../agent-prompts/WS-03-oss-precedents.md). Cargo represents package management; Alembic represents database migration tooling; JSON Schema represents schema/constraint systems. These representatives do not stand for every implementation in their family. Camel is the concrete domain-owned OpenRewrite case, not a thirteenth independent engine.

Capability descriptions are **DOCUMENTED** by the primary sources cited in each row. Role classifications, authority limits, and reuse recommendations are **INFERRED** unless otherwise marked. Test facilities describe what maintainers can run, not test results observed in this investigation. The complete uniform records and source catalog, including access dates and section locators, are in [structured/open-source-precedents.json](../structured/open-source-precedents.json).

Two panels form one matrix keyed by precedent ID. Separating panels keeps ownership/packaging distinct from execution/provenance. Roles: **D** declarative knowledge; **T** transformations; **P** policy decisions; **O** orchestration; **V** validation. A role denotes an exercised capability, not an exclusive category or universal guarantee.

## Licensing and maintenance boundaries

- **DOCUMENTED:** GitHub's CodeQL query/library repository is MIT, but its README distinguishes the separately licensed CLI and commercial use requirements. Open queries do not establish an open analysis engine (S03).
- **DOCUMENTED:** Semgrep CE is open source; its README distinguishes proprietary capabilities and rules. Do not label its entire registry/platform OSS (S13).
- **DOCUMENTED:** Terraform Plugin Framework is MPL-2.0 (S20); current Terraform core uses Business Source License 1.1 with an additional use grant and later change license (S21). The provider framework is the OSS precedent here, not an assertion that current core is OSI-open-source. Provider licenses require individual review.
- **DOCUMENTED:** Camel recipes are Apache-2.0 (S02); Alembic is MIT (S30). OpenRewrite's current testing documentation references authenticated artifact distribution; a reusable API does not imply every recipe artifact is freely available from Maven Central (S01).
- **DOCUMENTED:** The Roslyn SDK repository is archived and points to dotnet/roslyn (S08). The old rustfix repository is archived and points to Cargo's crates/rustfix (S10). Archive status is not evidence the abstraction is abandoned.
- **INFERRED:** License, runtime compatibility, artifact access, domain ownership and deployment authorization are separate acceptance checks. This is not a comprehensive license audit.

## Terminology collisions and reuse

| Proposed wording/capability | Existing abstraction | Assessment |
| --- | --- | --- |
| Executable domain knowledge package | Recipe library, query/model pack, analyzer package, rule set | **INFERRED:** New wording describes existing artifacts; no new format needed for this alone (P01-P06). |
| Independently owned decisions | Policy-as-code, policy bundle, evaluator plus enforcement point | **INFERRED:** OPA directly supplies much of the proposed boundary; do not claim the principle is new (P07). |
| Domain understands operational transitions | Provider plugin, operator/controller, migration graph | **INFERRED:** These encode actions and state evolution already, sometimes including orchestration that MEDP wants separate (P08-P09, P12). |
| Portable constraints and validator agreement | JSON Schema dialect, vocabulary and conformance suite | **INFERRED:** This already tests interpretation across implementations; portability needs a conformance corpus, not only a schema (P10). |
| Package identity and compatible versions | Native package coordinates, dependency constraints and lockfiles | **INFERRED:** Reuse ecosystem identities; a common wrapper must not hide unresolved engine/toolchain dependencies (P01-P02, P08, P11). |
| Explanations tied to evidence | Diagnostic IDs/locations, rule messages, decision records | **INFERRED:** Existing mechanisms cover parts of challengeability; authored explanations and logs are not proofs of a decision's correctness (P04, P06-P07). |

**DOCUMENTED reusable interfaces:** JSON Schema 2020-12 includes vocabulary/meta-schema and recommended output schemas (S24). Terraform has an explicit plugin protocol (S17). Rust diagnostics already cross the knowledge producer/fix-applier boundary (S09-S10). CodeQL packs define versioned model extension targets (S04). These are standards or ecosystem contracts with different scopes, not one interchangeable universal protocol.

**OPINION:** Preserve native recipe, query, policy, schema and package formats first. Evaluate existing distribution and provenance standards separately if WS-09 needs them; this review does not establish SARIF, OCI, SLSA or in-toto as a complete solution to domain authority. MCP is a possible call surface, not what makes the knowledge executable or trustworthy; Semgrep already supplies a direct counterexample to agent-access novelty (S13).

## What remains unproven

**HYPOTHESIS:** A thin composition boundary could help connect heterogeneous observations, policy decisions, transforms and validation results while preserving each publisher's authority and identifying disagreements. None of the reviewed sources establishes a single shared contract spanning that entire workflow. This is a bounded literature finding, not proof that no existing system does so.

The useful missing behavior would need to be demonstrated, not inferred from giving familiar components a shared name:

1. **Cross-engine evidence identity:** connect a particular observation snapshot, rule/package content, policy revision and validation result without replacing their native meanings.
2. **Separate authorities:** distinguish a community-supported transformation from provider advice, organization permission and user choice; report conflicts rather than flattening them into one recommendation.
3. **Comparable outcomes:** two clients using the same complete execution context agree on supported, blocked, unsupported and unknown outcomes, including skipped checks and errors.
4. **Challenge handling:** show which observation, rule or authority changed when a decision is disputed; do not let agent prose silently become a new rule.

**INFERRED:** Existing CLIs plus a small integration service may satisfy all four. A new archive format or DSL is not a prerequisite. Rules with clocks, remote data, differing parsers or mutable references defeat naive replay even when the visible input and package version look identical.

## Implications for WS-09 and WS-10

**WS-09, constraints rather than a specification:** inventory native artifacts before inventing fields; keep package identity distinct from digest, signer, authority, evidence and run ID. Preserve engine prerequisites and unsupported cases. Require justification for every field that duplicates a native manifest or result format. Do not translate recipe/Rego logic into an LLM-authored substitute DSL merely to make the wrapper uniform.

**WS-10, proposed falsification experiment (not executed):** use a pinned Camel/OpenRewrite recipe, a separately owned OPA policy and existing validators through their native interfaces. Compare a plain CLI/library composition against the proposed control-plane wrapper on the same snapshots. A fixed script and an agent client should both consume the same decision service without reimplementing domain rules. Include a supported migration, Camel-Quarkus unsupported case, organization denial, missing observation, engine incompatibility, changed policy revision and failed validator. Keep transformations in disposable worktrees; deny writes to policy/runtime configuration to the client.

Record resolved artifacts and engine versions, observation hashes, selected rules, policy decisions, reasons, edits, validation outputs and enforced versus merely reported denials. An unsupported/skipped/error outcome must not become success. If the native composition already yields equivalent outcomes and an adequate audit trail, **drop the new package format**. If the wrapper reduces duplicated adapters or prevents a concrete authority/provenance failure, report that measured improvement as integration value, not invention of executable knowledge.

## Bottom line

**INFERRED:** MEDP currently names a composition hypothesis, not a demonstrated necessary abstraction. The closest existing artifact is a tested recipe library; OPA is the strongest counterexample to authority/decision novelty; operators are the clearest prior terminology for operational expertise made executable. Durable value may still lie in maintained domain content, conformance tests, trusted publication and effective enforcement. This review does not establish their economics or the necessity of a new package standard.
