DOMAIN PACKS / SPECIMEN 001concept · hackathon morning

THE AGENT SHOULD NOT OWN THE EXPERTISE.

Domain knowledge becomes infrastructure.

Machine-executable domain packs turn stable expertise into typed observations, rules, legal moves, transformations, knowledge and verification — reusable by any agent.

01 / COMPILE

Extract what can be known without asking a frontier model.

02 / CONSTRAIN

Expose legal next moves instead of asking the model to invent them.

03 / SHARE

Let communities maintain public expertise once, for every agent.

Enter the runtime ↓

STATE / 00 — THE DEFAULT

A smart agent keeps rediscovering the same world.

Give a frontier model a repository and it can infer a lot. But compatibility rules, upgrade order, known API migrations and validation logic are stable. Re-inferring them every run is expensive and inconsistent.

general model → repeated domain reasoning

STATE / 01 — COMPILE THE DOMAIN

Move stable expertise out of the model.

A domain pack is not “some RAG.” It is executable expertise: observations, rules, transformations, process graphs, knowledge and verification.

domain expertise → typed substrate

STATE / 02 — THE RUNTIME LOOP

Assess. Constrain. Plan. Execute. Verify.

The pack turns a messy codebase into typed observations, derives legal moves, compiles them into a task graph, lets an agent resolve ambiguity, then verifies the result deterministically.

fuzzy intent → legal action → evidence

STATE / 03 — MCP IS THE PORT

MCP can make packs discoverable. It should not be the knowledge model.

The agent asks a registry which pack applies, calls typed tools such as inspect, legal_moves, plan and verify, and gets versioned JSON back. The pack remains usable from a CLI or library too.

agent ⇄ MCP ⇄ domain pack

STATE / 04 — THE COMMONS

Public domains can have public packs.

Language maintainers, framework authors, security communities and tool vendors could maintain executable knowledge once. Organization-specific policy can layer on top without forking the commons.

community expertise → shared machine substrate

NORTH STAR / OBVIOUSLY

Rewrite it in Rust.

The deliberately unreasonable demo target is useful because it makes the architecture visible: observe the source, identify a narrow supported slice, expose legal Rust targets, compile a plan, let the model fill the gaps, then prove it with cargo check and tests.

because apparently everything ends up in Rust

A SMALL PROTOTYPE THAT PROVES THE IDEA

One pack. One transformation. One agent-independent contract.

Base contract

Versioned JSON Schema envelopes for observations, legal moves, task DAGs and verification evidence. Packs may add domain-specific payload schemas.

MCP adapter

Expose pack discovery and execution through MCP, but keep the core pack callable from a CLI/library so MCP never becomes the ontology.

First demo

Translate a deliberately tiny ASP.NET Minimal API subset to Rust/Axum. Unsupported constructs are surfaced as typed blockers, not guessed around.

Success condition

Two different agents can consume the same pack and arrive at the same legal plan and verification criteria, even if their generated code differs.
