Where does the intelligence actually live?

The easy story is: Agent = how, Skill = what it knows, MCP = what it can do. Useful. But only partly true.

Agent
Policy & orchestration

Role, workflow, scope, approval gates, tool permissions.

Mostly visible
Skill
Reusable competence

Knowledge, procedure, scripts, examples — or sometimes just a route to something elsewhere.

Visibility varies
MCP
External capability

Tools, authoritative data, services and actions beyond the local prompt.

Contract visible, internals maybe not
The catch
A skill can look like expertise while the real expertise lives somewhere else.

So the useful question is not “does this agent have a skill?” but “what makes this agent competent, and can I inspect it?”

A better model

Four places knowledge can live

Knowledge does not map one-to-one to Agent, Skill or MCP. It is distributed.

1. Explicit knowledge
Rules, mappings, checklists, examples, compatibility tables.
Usually yours / visible
2. Contextual knowledge
Facts about this application, business constraints, architecture, current state.
Yours + connected systems
3. Operating policy
Who may do what, when approval is required, which tools are allowed.
Custom configuration
4. Latent expertise
Pattern recognition, synthesis, architectural judgment, fuzzy interpretation.
Mostly model provider
Not all skills are equal

What you can govern directly

Agents, skill contents, declared dependencies, permissions, versions, local data sources and observable outputs.

What you govern indirectly

Latent model expertise and proprietary services: you cannot inspect the internals, so you constrain, test, evaluate and observe behavior.

Your architecture lens

Where the semantic compiler fits

Instead of asking the big model to rediscover structure from raw context every time, a deterministic or highly constrained layer can turn messy input into typed, inspectable primitives first.

1

User input

Messy request, company language, repo state, documents.

Yours
2

Custom context

Agent policy, Skills, business rules, connected data.

Mostly yours
3

Semantic compiler

Normalize, type, constrain, resolve known rules, produce legal options or structured state.

Open / buildable layer
4

Big LLM

Synthesis, ambiguity, trade-offs, language, expert-like judgment.

Provider expertise
5

MCP actions

Execute, query authoritative systems, validate and return evidence.

Mixed ownership
Deterministic where possibleLLM where ambiguity is valuableExternal tools where authority matters
The semantic compiler is the area where you can move intelligence out of the opaque model and into inspectable software.

Not everything should move there. But typing, routing, validation, policy checks and legal-next-action generation often can.
