case / Apache Camel modernization

A concrete non-Microsoft case

The community
owns the migration.

Apache Camel is a strong test case for machine-executable domain packages: the project community already writes the migration guides, knows the breaking changes, and publishes automated upgrade recipes. The agent does not need to own that knowledge.

The proposed split:

Community — defines and reviews domain truth
Package — executable observations + transitions
Agent — handles gaps and ambiguous local context
Maintainer — approves policy and risky choices

01 / Why Apache Camel

A domain with living, distributed expertise.

Camel releases frequently, carries years of migration knowledge, and already says: some upgrade work can be automated; some still requires human migration.

That incompleteness is exactly what makes it useful. We can clearly separate known community transformations from the places where an LLM is actually valuable.

02 / Today: expertise starts as prose

The community already knows what changed.

Camel's own migration guide records hard facts: Java 11 support is dropped, components disappear, alternatives are suggested, endpoint behavior changes, and release-to-release upgrade notes accumulate.

migration guide → human-readable domain knowledge

03 / Compile the guide

Turn stable truths into executable transitions.

The package observes the repo, types what it finds, and exposes only transformations the community has encoded and tested. OpenRewrite recipes are a natural implementation substrate.

observe → type → match → legal recipe

04 / Example

A removed component is not an invitation to improvise.

If the project uses camel-rabbitmq, the Camel migration guide names spring-rabbitmq-component as the alternative. That relationship can live as versioned community knowledge, not as a fact a model reconstructs on every run.

camel-rabbitmq → spring-rabbitmq-component

05 / The gap is where the agent starts

Recipes stop at local meaning.

Maybe your route relies on custom headers, bespoke error semantics, or an internal wrapper around the removed component. The package can say “known migration exhausted.” Only then does a coding agent need to reason over local context.

known recipe exhausted → agent task + review required

06 / Verification

The community package defines what “done” means.

Build on Java 17, run tests, search for removed artifacts, verify route startup. The model can write code; the package carries the acceptance contract.

transform → compile → tests → forbidden-pattern check

07 / The governance loop

A migration improvement becomes a pull request.

A maintainer discovers a new recurring edge case, contributes a recipe or validator, reviewers approve it, a package version is released, and every agent can consume the improvement.

field evidence → PR → review → package release → ecosystem

08 / The boundary

Community truth first. Agent judgment second.

The package should not try to encode every application on earth. It should encode the repeatable parts so the LLM spends its intelligence only on what remains irreducibly specific.

stable domain → package / novel local context → agent

09 / Why this is better than “ask Claude”

The package accumulates community memory.

The value is not that an LLM could never discover these migrations. It often can. The value is that the community can encode a known transformation once, test it once, version it, review it, and let every model reuse it without repeatedly reconstructing the same truth.

11 / Thesis

Improve the domain
with a pull request.

Don't make every model relearn the same migration.

Why Camel: the Apache project publishes detailed 3→4 and 4.x migration guides, including a Java 17 baseline, removed components and suggested alternatives. Camel also points users to Camel Upgrade Recipes for automated assistance, while explicitly noting that some migration remains manual.

Related precedent: OpenRewrite maintains composable migration recipes, and its community recipe index lists Apache Camel, Apache Wicket, AWS SDK, AxonFramework and other projects. Quarkus similarly maintains update recipes and invites contributions. This specimen proposes a packaging/governance abstraction around those existing mechanisms.
