Modernize / JEV / semantic compile

A case study in what an “agent” is actually made of

Who owns
the domain?

Microsoft Modernize looks like an AI agent from the outside. Inside, much of the valuable work is already typed, routed, rule-bound and verified. The interesting question is not “agent or no agent?” It is where each kind of intelligence belongs.

Four layers keep getting collapsed into one word: agent.

Human input — goals, policy, exceptions
Domain knowledge — what is true / supported
Semantic compile — typed state + legal moves
Large LLM — ambiguity, synthesis, novel work

01 / Why JEV is interesting

Not every intelligent choice is a generation problem.

If the legal next moves are already known, a frontier model may be an extravagant way to choose among them.

The attraction of JEV-like systems is architectural: split decision from generation. Better yet, compile stable structure out of the messy input before a large model ever sees it.

Good candidate for semantic compile

version, capability, compatibility, dependency, policy, legal transition, validation

Good candidate for large LLM

ambiguous intent, incomplete business context, novel architecture, unsupported code synthesis

02 / The misleading outside view

“The agent modernizes the app.”

That sentence is convenient and almost useless. It hides which work is language understanding, which is encoded domain expertise, which is deterministic analysis, and which is verification.

problem → one giant agent-shaped blob

03 / First split

Assessment is already a semantic front-end.

In our PhotoAlbum run, .NET AppCAT emitted rule IDs, exact files and lines, target-specific severity, framework, language, toolchain and effort. That is not Claude “understanding the repo” from scratch.

source → AppCAT → typed incidents

04 / Domain knowledge enters

Facts only matter because the domain knows what they mean.

“Windows Authentication detected” becomes actionable because compatibility knowledge says which targets support it, which migrations are legal, and which constraints apply. Modernize combines these findings with rulebooks and supported patterns.

typed facts + domain rules + policy → candidate work

05 / Where the big model earns its keep

The LLM bridges typed machinery and messy intent.

Planning still has to reconcile human language, repository specifics, business constraints and gaps in the recipe catalog. This is exactly where a large model is useful — not because every step is fuzzy, but because some are.

human intent ↔ planner ↔ tasks.json

06 / Ground truth returns

The compiler gets the final vote.

Specialist executors may generate or transform code, but builds, tests, scanners and deployment checks verify the result. Probabilistic work is enclosed by deterministic evidence.

execute → build → test → scan → evidence

07 / Reframe

The architectural question becomes an ownership question.

Microsoft can afford to encode .NET expertise deeply — and has every incentive to guide modernization toward its own stack. But for Java, Python, Kubernetes or databases, should the executable domain layer belong to one agent vendor?

who owns the machine-readable truth?

08 / The open alternative

Package the domain. Let agents consume it.

OpenRewrite already shows the pattern: semantic trees and composable migration recipes maintained across communities. The next abstraction is a portable contract that bundles observations, rules, transitions, recipes, validators and provenance.

09 / Evidence from the morning

The “AI assessment” was mostly not AI.

The raw PhotoAlbum assessment identifies itself as .NET AppCAT CLI. Its recorded analysis window is roughly one second. The report contains structured incidents, exact locations, target-specific severity and effort. That is already a typed intermediate representation.

The multi-minute Modernize experience therefore includes orchestration, downloads, reporting and model-mediated work around a very fast deterministic analyzer.

10 / Where the value sits

The expensive thing may be encoding the domain, not calling the model.

Modernize is evidence for both sides of the argument.

Heavy domain engineering buys repeatability, lower variance, policy, provenance and cheaper runtime decisions. General models buy breadth and lower setup cost. The design problem is finding the break-even point.

11 / The critique

Closed knowledge is useful — until it becomes the only machine-readable knowledge.

Domain truth

“Spring API X is incompatible with Spring 3.” This belongs close to the community/upstream.

Vendor guidance

“For Azure, migrate X to service Y.” Valuable, but explicitly vendor-scoped.

Organization policy

“Use PostgreSQL; no public endpoints.” Local authority, versioned separately.

Agent judgment

“Given these constraints, choose path B.” Probabilistic and reviewable.

12 / Thesis

Compile the domain.
Rent the intelligence.

Build software with LLMs — not software out of LLMs.

Design approach: editorial rather than SaaS; one fixed scene with state accumulation, followed by one reframe into ownership. Continuity anchor: the same modernization “decision object” persists while its representation changes.
